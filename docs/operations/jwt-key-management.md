# Управление JWT-ключами

## Где хранятся ключи

Локальный профиль использует отдельный тестовый ключ из `application-local.yml`.
Он не должен использоваться в production. Без keyring production-профиль не
запускается.

На VPS Compose монтирует в контейнер приложения только файл
`jwt-keyring.properties`. Путь к файлу на хосте задаётся переменной
`JWT_KEYRING_FILE` (по умолчанию `./secrets/jwt-keyring.properties`). Каталог
`secrets/` исключён из Git. Ограничьте доступ к каталогу и файлу пользователем,
который запускает Docker Compose.

Формат keyring:

```properties
security.jwt.active-key-id=prod-2026-10
security.jwt.keys.prod-2026-10=<random-secret-at-least-32-bytes>
```

Секрет должен быть криптографически случайным и не короче 256 бит. Создайте
его генератором случайных данных, например `openssl rand -base64 48`, и
поместите в файл напрямую, не добавляя значение в Git, shell history или логи.
На VPS задайте права файла `0600`, каталога `0700`.

Сервис приложения доступен в Compose под профилем `production` и ожидает готовый
образ, указанный через `APPLICATION_IMAGE`. Например, запуск выполняется с
`docker compose --profile production up -d`. Для локального запуска
инфраструктуры профиль приложения включать не нужно.

## Плановая ротация

1. Сгенерируйте новый случайный ключ и добавьте его в keyring под новым,
   никогда ранее не использованным `kid`.
2. Переключите `security.jwt.active-key-id` на новый `kid`. Старый ключ оставьте
   в `security.jwt.keys` для проверки ранее выданных JWT.
3. Перезапустите приложение и проверьте выпуск токена с новым `kid` и принятие
   токена, подписанного старым ключом.
4. После истечения максимального срока действия токенов старого ключа
   (30 дней после выдачи последнего токена этим ключом) удалите его запись и
   снова перезапустите приложение.

## Компрометация ключа

Немедленно удалите скомпрометированный `kid` из keyring и активируйте новый
ключ. JWT с отозванным `kid` сразу перестанут проходить проверку. Пользователям,
чьи сессии использовали этот ключ, потребуется войти заново; refresh-сессия
сама по себе не позволяет обойти проверку подписи refresh JWT.
