# Бэклог разработки

Этот файл — основной локальный список этапов и задач проекта. Крупные направления называются **эпиками**, конечные единицы работы — **задачами**. Идентификаторы сохраняются при переносе задач в GitHub Issues, Linear или другой трекер.

Архитектурные границы и принципы описаны в [обзоре архитектуры](../architecture/overview.md). Внутренние задачи бизнес-модуля добавляются только после отдельного обсуждения этого модуля.

## Статусы

- `TODO` — готово к выполнению.
- `IN PROGRESS` — выполняется.
- `BLOCKED` — есть конкретная зависимость или препятствие.
- `DISCUSSION REQUIRED` — сначала нужно обсудить область и согласовать план.
- `DONE` — критерии приёмки выполнены.

## Порядок работы с модулями

Перед реализацией каждого нового бизнес-модуля:

1. Обсудить назначение модуля, сценарии, границы данных и зависимости.
2. Зафиксировать согласованные решения и открытые вопросы в `docs/roadmap/modules/<module>.md`.
3. Разбить согласованный план на задачи с проверяемыми критериями приёмки.
4. Только после этого брать задачи в реализацию.
5. В конце сессии обновлять статусы и кратко записывать оставшийся следующий шаг здесь.

Так следующая сессия может продолжить с первой готовой задачи, не повторяя обсуждение уже принятых решений.

## Эпик ID — identity и авторизация

Цель: завершить модуль аутентификации от OTP-запроса до защищённого endpoint.

- [x] `ID-01` Пройти полный JWT flow через HTTP.
  - Запросить OTP и определить dev-способ получить его локально.
  - Выполнить login, получить access и refresh токены.
  - Выполнить refresh и проверить защищённый endpoint новым access token.
  - Приёмка: весь сценарий работает последовательно через HTTP.
  - Результат: при профиле `local` OTP возвращается в поле `debugCode`; без профиля код не раскрывается. Проверены login, access token на `/api/v1/auth/me`, refresh и новый access token на том же endpoint.
- [x] `ID-02` Завершить тестирование `identity`.
  - Domain, application, infrastructure, API и Spring Context.
  - Приёмка: тесты проходят; основные отрицательные сценарии покрыты.
  - Результат: 63 теста identity и 1 Spring MVC integration test прошли; дополнительно Maven reactor прогнал 5 тестов common-core. Покрыты OTP/account rules, refresh-token сценарии, JWT validation, API flow, security filter и создание Spring-контекста.
- [x] `ID-03` Подключить PostgreSQL persistence.
  - PostgreSQL через Docker Compose, миграции схемы и persistence adapter в `identity`.
  - Использовать существующую доменную модель `UserAccount`; не дублировать её в domain.
  - Решение: использовать Liquibase для версионирования и применения миграций.
  - Уникальность телефона и транзакционность операций.
  - Заменить in-memory account storage на PostgreSQL adapter.
  - Результат: PostgreSQL поднят через Docker Compose; Liquibase YAML changelog создал таблицы учётных записей и ролей. Hibernate проверил схему, полный OTP/JWT HTTP integration test прошёл с PostgreSQL. `./mvnw -pl application -am test` завершился успешно.
- [x] `ID-04` Подготовить авторизацию к production.
  - Статус: `IN PROGRESS`; задачи `ID-04.1` и последующие выполняются по одной.
  - [x] `ID-04.1` Перенести OTP-хранилище и лимиты запросов в Redis.
    - Решения: TTL OTP — 3 минуты; максимум 5 неверных попыток; повторный запрос не чаще одного раза в минуту и не более 5 раз за 15 минут на номер телефона; дополнительно общий лимит для endpoint выдачи OTP — 20 запросов за 15 минут и 100 за сутки с одного IP, суммарно по всем номерам.
    - Приёмка: OTP истекает в Redis по TTL; успешный код нельзя использовать повторно; попытки и лимиты корректно работают при параллельных запросах и нескольких экземплярах приложения.
    - Результат: Redis-хранилище с TTL и атомарной проверкой OTP через Lua; атомарные sliding-window лимиты по телефону и IP; доверенный `X-Forwarded-For` учитывается только от настроенных proxy; номер телефона хешируется в ключе Redis; `429` возвращает `ProblemDetail` и `Retry-After`. Чистый Maven reactor прошёл, 7 integration-тестов проверили TTL, одноразовую проверку, 5 попыток, HTTP-ответ и параллельные OTP/IP запросы.
  - [x] `ID-04.2` Добавить управляемые refresh-сессии и ротацию токенов.
    - Решения: access token — 15 минут, refresh token — 30 дней; у каждого устройства отдельная сессия; хранить в PostgreSQL хеш refresh token и состояние сессии, не исходный токен.
    - Приёмка: каждый refresh атомарно инвалидирует старый refresh token и возвращает новую пару access/refresh; повторное использование старого токена отзывает цепочку только этой сессии; параллельное обновление не создаёт две активные ветки.
    - Результат: PostgreSQL хранит сессии и историю только хешей refresh-токенов; каждый refresh возвращает новую пару; блокировка строки сессии сериализует параллельные обновления; повтор старого токена отзывает только его сессию. JWT получают уникальный `jti`; истёкшие сессии удаляются при создании/обновлении новой.
    - Проверка: Liquibase миграция применилась на PostgreSQL 17; `./mvnw -pl application -am test` прошёл — 78 тестов, включая HTTP refresh flow, параллельную ротацию и изоляцию сессий.
  - [x] `ID-04.3` Добавить завершение refresh-сессий.
    - Решения: поддержать выход с текущего устройства и выход со всех устройств пользователя; access token может оставаться действительным до истечения срока, максимум 15 минут.
    - Приёмка: отозванная refresh-сессия не может получить новые токены; отзыв одной сессии не завершает другие; выход со всех устройств отзывает все refresh-сессии пользователя.
    - Результат: `POST /api/v1/auth/logout` отзывает сессию по refresh token только для владельца текущего access token; `POST /api/v1/auth/logout-all` отзывает все refresh-сессии пользователя. Оба endpoint-а возвращают `204`; выход идемпотентен. Уже выданный access token действует до истечения своего срока.
    - Проверка: `./mvnw -pl application -am test` завершился успешно; 75 тестов прошли, включая HTTP-проверки выхода с одного устройства, изоляции чужих сессий и выхода со всех устройств.
  - [x] `ID-04.4` Убрать небезопасный JWT secret по умолчанию и внедрить управление ключами.
    - Решения: оставить HMAC; добавлять в JWT `kid`; новый ключ использовать для подписи, предыдущие временно принимать только для проверки; планово менять ключ раз в 30 дней и сохранять старый для проверки до истечения выданных им токенов (максимум 30 дней с последнего токена); при компрометации немедленно отзывать ключ и требовать повторный вход для затронутых сессий.
    - Решение для первого production-развёртывания: один арендованный VPS и Docker Compose; секреты поступают из защищённых файлов вне Git и передаются контейнеру через Compose secrets. Self-hosted Vault на том же VPS не разворачивать; внешний secret manager рассмотреть при появлении нескольких серверов/окружений.
    - Приёмка: без настроенного секрета приложение не запускается вне локального профиля; секреты не хранятся в Git; локальная конфигурация явно отделена от production; неизвестный или отозванный `kid` отклоняется; Compose предоставляет приложению только назначенные ему секреты.
    - Результат: убран JWT secret по умолчанию; production требует внешний `jwt-keyring.properties`, локальный ключ вынесен в `application-local.yml`; выпущенные токены содержат `kid`, проверка использует только настроенный keyring; Compose монтирует приложению только keyring как Docker secret. Инструкция ротации и отзыва ключа: `docs/operations/jwt-key-management.md`.
    - Проверка: `./mvnw -pl application -am -DskipTests package` прошёл, включая компиляцию тестовых исходников. Автоматические тесты не запускались.
  - [x] `ID-04.5` Привести ошибки auth API к `ProblemDetail`.
    - Решение: использовать формат ошибок legacy-приложения как основу.
    - Приёмка: ошибки валидации и авторизации имеют согласованные HTTP-статусы и структуру; ответы не раскрывают OTP, токены, секреты или внутренние исключения.
    - Результат: ошибки auth API возвращаются в `ProblemDetail` с `status`, `title`, `detail` и `path`; ошибки валидации дополнительно содержат `fieldErrors`. Некорректный запрос — `400`, ошибка аутентификации — `401`, запрет доступа — `403`, конфликт данных — `409`, внутренняя ошибка — безопасный `500`; rate limit остаётся `429` с `Retry-After`. JWT-фильтр и Spring Security handlers тоже возвращают ProblemDetail. Неверный OTP и refresh token дают одинаковый общий ответ без раскрытия причины.
    - Проверка: `./mvnw -pl application -am -DskipTests package` прошёл, включая компиляцию тестовых исходников; автоматические тесты не запускались.
  - Для IP-лимита учитывать `X-Forwarded-For` только за доверенным reverse proxy; иначе использовать адрес соединения.
  - Для Compose-файла секреты задавать как внешние файлы с хоста; ограничить права чтения на VPS и не добавлять файлы в репозиторий.

## Эпики бизнес-модулей

Порядок соответствует согласованному плану. Каждый эпик остаётся на `DISCUSSION REQUIRED`, пока мы отдельно не обсудим модуль и не создадим его план и задачи.

- `DISCUSSION REQUIRED` `MOD-USER` — профиль, персональные данные и адреса.
- `DISCUSSION REQUIRED` `MOD-FRANCHISE` — владельцы и дарксторы.

- `DISCUSSION REQUIRED` `MOD-INVENTORY` — остатки и доступность товаров.
- `DISCUSSION REQUIRED` `MOD-CART` — корзина.
- `DISCUSSION REQUIRED` `MOD-ORDERING` — заказы.

Для каждого пункта до обсуждения не создаются предположительные задачи реализации. После обсуждения у эпика появится файл `docs/roadmap/modules/<module>.md` с решениями, зависимостями, задачами и критериями приёмки.
